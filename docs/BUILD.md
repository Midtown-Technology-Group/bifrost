## Reproducible builds

Every build input is pinned, so rebuilding the same commit from a clean
checkout resolves the identical dependency closure and base layers:

| Input | Pin | Source |
|---|---|---|
| Python dependencies | Exact versions + sha256 hashes (`--require-hashes`) | `requirements.lock` (generated by `pip-compile --generate-hashes` from `pyproject.toml`; regen command is in the lockfile header) |
| Type-check-only Python deps | Same hash-pinned scheme | `requirements-pyright.lock` (dev images only) |
| Node dependencies | Exact resolved tree | `client/package-lock.json`, installed with `npm ci` (never `npm install`) |
| Container base images | Digest-pinned (`@sha256:…`) | `api/Dockerfile`, `api/Dockerfile.dev`, `client/Dockerfile`, `client/Dockerfile.dev`, `client/Dockerfile.playwright` |
| GitHub Actions | Commit-pinned (`uses: …@<sha> # vX.Y.Z`) | `.github/workflows/*.yml` |
| Build version stamp | Commit-derived | `BIFROST_VERSION` / `VITE_BIFROST_VERSION` (see below) |

Reproduce from a clean checkout:

```bash
git clone https://github.com/Midtown-Technology-Group/bifrost.git
cd bifrost
./setup.sh              # operator path: writes .env with random secrets
docker compose up --build
```

No network-fetched unpinned inputs exist in the build path: `pip install`
runs with `--require-hashes --only-binary :all:` (no source builds, no
`pip install --upgrade`), and `npm ci` reproduces `package-lock.json`
exactly. CI rebuilds release images from clean checkouts on every `v*` tag
(`build-api`, `build-client`, `build-worker` lanes in
`.github/workflows/ci.yml`), and every PR build starts from a fresh runner.

## Docker-based builds

| Dockerfile | Purpose |
|---|---|
| `api/Dockerfile` (`runtime` target) | Production API / scheduler / worker image |
| `api/Dockerfile.dev` | Dev image: same pinned base + deps, code via volume mounts, hot reload |
| `client/Dockerfile` (`production` target, nginx) | Production client; `ci` target runs `tsc` + `lint` + unit tests |
| `client/Dockerfile.dev` | Dev image: deps only, source via volume mounts, Vite HMR |
| `client/Dockerfile.playwright` | Pinned Playwright browser image for client E2E |

Compose files select the stack, never hidden flags:

| File | Use |
|---|---|
| `docker-compose.yml` | Production/operator stack (`./setup.sh`, then `docker compose up`) |
| `docker-compose.dev.yml` | Dev overlay used by `./debug.sh` |
| `docker-compose.debug.yml` / `docker-compose.debug.port.yml` | Debug boot modes (Netbird vs local port) |
| `docker-compose.test.yml` | `./test.sh` test stack (Postgres, Redis, RabbitMQ, SeaweedFS, API, worker) |
| `docker-compose.docs.yml` | Docs preview |

CI build lanes (`.github/workflows/ci.yml`): `build-candidate-images`
(PR/merge-group candidate images with attestation + keyless cosign signing),
`build-dev` (main-push dev images), `build-api` / `build-client` /
`build-worker` (signed release artifacts per `v*` tag), plus `nightly.yml`
for nightly rebuilds.

## Standard build variables

| Variable | Meaning | Default | Set by |
|---|---|---|---|
| `BIFROST_VERSION` | API/worker image version stamp (Docker `ARG`, baked at build) | `unknown` (`debug` under `./debug.sh`, from `git describe --tags --always --dirty`) | `debug.sh`, `test.sh` (`--build-arg`), CI release lanes |
| `VITE_BIFROST_VERSION` | Client version stamp (Docker `ARG` → `ENV`, compiled into the Vite bundle) | `unknown` | Same as above; nightly uses `nightly-<sha>` |
| `COMPOSE_PROJECT_NAME` | Compose isolation scope, derived per worktree via `compute_project_name` (`scripts/lib/test_helpers.sh`) | `bifrost-debug-<hash>` / test-stack equivalent | `debug.sh`, `test.sh` (always exported; parallel worktrees never collide) |
| `BIFROST_API_UPSTREAM`, `BIFROST_RENDERER_*`, `BIFROST_CANONICAL_SCHEME` | nginx upstream wiring (production client image) | `api:8000`, loopback renderer, `http` | `client/Dockerfile` (`ENV` + `NGINX_ENVSUBST_FILTER`) |

Env layering for local stacks (later wins, process env wins everything):
repo `.env` → `.env.debug` → `~/.config/bifrost/debug.env`
(per-user overrides such as `NETBIRD_SETUP_KEY`). No native-binary
compilation takes tuning flags: Python deps install prebuilt wheels only
(`--only-binary :all:`) and the JS toolchain is prebuilt, so there are no
`CC`/`CFLAGS`/`LDFLAGS` inputs to honor or override.

## Debug vs production builds

Dev images are the production Dockerfiles' debug-preserving siblings, not
stripped-down forks:

- **No stripping, anywhere.** No `strip`, no `install -s`, no
  `PYTHONOPTIMIZE`; the dev API image sets only `PYTHONDONTWRITEBYTECODE=1`
  (suppresses `.pyc` writes so host checkouts stay clean — it removes no
  debug information).
- **API (dev):** `uvicorn … --reload` watches `/app/src` + `/app/shared`;
  scheduler/worker restart via `watchmedo` on the same trees
  (`docker-compose.debug.yml`). `ENABLE_DEBUG=true ./debug.sh` exposes the
  debugger on port 5678 and the API waits for attach.
- **Client (dev):** Vite dev server with HMR on port 80 (same port as
  production nginx); production (`client/Dockerfile`) serves the `vite build`
  bundle from nginx with unprivileged `nginx` user and read-only-friendly
  `755`/`644` dist permissions.
- **Logging:** dev stacks stream per-service logs via
  `./debug.sh logs <svc>` (also exported under `/tmp/bifrost-<project>/`
  after test runs); production logging configuration is unchanged code —
  verbosity is runtime env, not a separate build.

## Non-recursive, bounded builds

The repo contains **no Makefiles and no recursive build invocations** —
there is no `$(MAKE)`, `make -C`, or subdirectory build hierarchy with
cross-dependencies to get wrong. Every build is a bounded, explicitly
ordered step list:

- Multi-stage Dockerfiles with named targets (`builder` → `runtime`,
  `base` → `builder` → `ci`/`production`); each `COPY`/`RUN` layer declares
  its inputs.
- CI lanes are linear step lists over pinned actions and digest-pinned base
  images (see [Reproducible builds](#reproducible-builds)); `build.sh`-style
  unbounded recursion does not exist.
- Dev/test launchers (`debug.sh`, `test.sh`) are verb-style scripts with a
  fixed subcommand surface (`up`, `down`, `status`, `logs`, …), not build
  systems — they orchestrate `docker compose` with an explicit file list.

## Installation

### Required tooling

| Tool | Version | Notes |
|---|---|---|
| Docker + Docker Compose | Recent (Compose v2 plugin) | Only hard requirement for every path below |
| Git | Any recent | `git describe` feeds `BIFROST_VERSION` under `./debug.sh` |
| Python | `>=3.11` (`pyproject.toml`); containers run 3.14-slim | Host Python needed only for helper scripts / direct CLI venv use |
| Node | `>=26.0.0` (`client/package.json` `engines`) | Host Node needed only for host-side client work (`./test.sh client unit`); containers carry their own |
| pipx | Any recent | Recommended installer for the `bifrost` CLI (isolated venv per tool) |

### Operator install (production compose)

```bash
git clone https://github.com/Midtown-Technology-Group/bifrost.git
cd bifrost
./setup.sh            # writes .env with secure random secrets
docker compose up -d  # client :3000, API via Vite proxy, Postgres/Redis/RabbitMQ
```

Windows operators use `Initialize-Bifrost.ps1` (same `.env` + compose flow).
Uninstall: `docker compose down -v` removes containers, network, and volumes.

### Developer install (debug stack, minutes)

```bash
git clone https://github.com/Midtown-Technology-Group/bifrost.git
cd bifrost
./debug.sh            # boots per-worktree isolated stack, prints URL + login
./debug.sh status     # URL, login, mode (port or Netbird)
./debug.sh down       # tears down + removes volumes for THIS worktree only
```

This single command installs the full working environment — API, client,
scheduler, worker, Postgres, RabbitMQ, Redis, SeaweedFS — with hot reload,
plus the test environment via the same convention:

```bash
./test.sh stack up    # boots the per-worktree test stack (once)
./test.sh             # unit tests (state auto-reset before each run)
./test.sh stack down  # tears it down + removes volumes
```

### CLI install (pipx, from a dev instance)

Install the API-matched CLI into an isolated venv without touching the
user's global environment:

```bash
mkdir -p /tmp/bifrost-cli && cd /tmp/bifrost-cli
python3 -m venv .venv && .venv/bin/pip install -q --upgrade pip
.venv/bin/pip install -q "<API_URL>/api/cli/download/bifrost-cli.tar.gz"
./.venv/bin/bifrost login --url <API_URL> --email dev@gobifrost.com --password password
```

or directly with pipx:

```bash
pipx install "<API_URL>/api/cli/download"
pipx install --force "<API_URL>/api/cli/download"  # upgrade to server build
```

The download endpoint serves the CLI built from the running API, so the CLI
always matches the server (a version-mismatch gate blocks drifted CLIs).
Uninstall: `pipx uninstall bifrost`.

## BadgeApp Silver justifications

Source of truth for the Silver answers below is
`scripts/generate-bestpractices-json.py` (overrides) → `.bestpractices.json`
(regenerated artifact). After merging to `main`, apply them on the
[Silver edit page](https://www.bestpractices.dev/en/projects/13022/silver)
via **Save (and continue) 🤖** — see
`docs/security/openssf-best-practices-badge.md`.

| Criterion | Status | Basis |
|---|---|---|
| `build_reproducible` | Met | Historical ID kept alongside `build_repeatable`; same evidence: hash-pinned lockfiles, digest-pinned bases, clean-checkout CI rebuilds |
| `build_repeatable` | Met | Same commit + pinned inputs → identical dependency closure; `npm ci`, `pip install --require-hashes`, digest-pinned bases, CI clean-checkout rebuilds |
| `build_standard_variables` | Met | All build parameterization flows through documented env/build-args (`BIFROST_VERSION`, `VITE_BIFROST_VERSION`, `COMPOSE_PROJECT_NAME`); no native compilation exists to take `CC`/`CFLAGS` (wheels-only pip, prebuilt JS toolchain) |
| `build_preserve_debug` | Met | Dev images preserve debug info: no stripping/`-O`/`install -s`; uvicorn `--reload`, watchmedo restarts, Vite HMR, optional debugger attach (`ENABLE_DEBUG=true`) |
| `build_non_recursive` | Met | No Makefiles, no recursive/subdirectory builds; bounded multi-stage Dockerfiles + linear CI lanes with pinned actions and base images |
| `installation_standard_variables` | Met | Container-native conventions: version-tagged images, `COMPOSE_PROJECT_NAME` isolation, layered env (`.env` → `.env.debug` → user overrides), standard ports |
| `installation_development_quick` | Met | `./debug.sh` boots the full dev stack in one command; `./test.sh stack up` boots the test stack; both per-worktree isolated |
| `installation_common` | Met | `setup.sh` + `docker compose` (operator), `./debug.sh` (dev), pipx CLI from the dev instance; uninstall via `docker compose down -v` / `pipx uninstall` |
