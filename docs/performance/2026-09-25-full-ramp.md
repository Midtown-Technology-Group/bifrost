# Issue 890 full concurrency ramp, 2026-09-25

The five-role external-HTTP lab completed a 1 → 4 → 16 → 32 → 64 → 128 → 4 recovery ramp. This extends the [earlier role-budget sweep](2026-09-25-role-budget.md) through the issue's requested 128-concurrent point. It is an **exploratory shared-host result**, not a production B3 capacity measurement.

On `bifrost-platform-test-debian13-01`, source `83fdde7c575134f96160eca0a4e9071e9d8eaff3` ran:

```bash
BIFROST_SKIP_BUILD=1 bash scripts/issue-890-run.sh \
  --scenario external-http --operations 200 \
  --concurrency 1 4 16 32 64 128 4
```

The run used Python 3.14.7, one API process, four worker slots, and the production-pinned client and renderer image digests recorded in the raw report. The API, scheduler, worker, client, and renderer shared CPU set `0-3`. The test-only API replica, PostgreSQL, PgBouncer, RabbitMQ, Redis, SeaweedFS, and load driver were outside that four-core application-role budget. Before startup the eight-vCPU host had about 5.5 GiB free on its root disk and two other test stacks were active. The lab stack was stopped after the report was copied; no other stack was changed.

There were no failed executions, stale worker pools, slot-timeout rejections, or memory-pressure rejections. Sampled worker occupancy reached four slots by concurrency 4. At 128, the one-second occupancy samples did not capture more than three busy slots, so the worker's instantaneous saturation at that level is unproven. Throughput flattened after concurrency 16 while most additional end-to-end latency appeared before claim; the running phase stayed near 0.2 seconds p95. After load returned to four, throughput and queue latency returned near the initial four-concurrent values without restart.

At concurrency 128, sampled average application-role CPU was about 0.36 API, 1.64 worker, 0.04 scheduler, and less than 0.01 each client and renderer cores. Peak sampled role cgroup memory was 358.3 MiB API, 233.0 MiB worker, 149.1 MiB scheduler, 5.3 MiB client, and 36.2 MiB renderer. These are individual peaks, not a simultaneous sum. The client and renderer received only startup/health traffic. PostgreSQL used about 0.22 core during this level and the test-only API replica about 0.02 core; neither was charged to the four-core application budget.

The result points to queue/worker-slot or setup pressure in this fixture before four application CPU cores are exhausted. It does **not** isolate the first saturated component or prove that Python is or is not the production bottleneck. Host contention, local dependencies, the short fixed-latency workflow, missing representative client/render traffic, and the non-B3 CPU/memory shape still limit cost inference. A quiet-host repetition and production role/wait telemetry are needed before assigning useful executions per B3-hour or selecting a Go subsystem.
