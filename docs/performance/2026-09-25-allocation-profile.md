# Issue 890 worker allocation profile, 2026-09-25

This is a diagnostic profile of the disposable external-HTTP workload on VM101 (`bifrost-platform-test-debian13-01`), not a production memory measurement. Source was `a681a848b7e44030b85365ea2dc55a0ec33fed0a`, Python 3.14.7, Memray 1.19.3, one API process, and four worker slots. The 200-execution, concurrency-64 run completed 200/200 without failures at 14.39 executions/s. The [load report](results/2026-09-25-memory-child-load.json) retains its timings and source metadata.

The worker launches its execution template with `subprocess.Popen`, and the template forks one child per execution. Memray's `--follow-fork` on the worker coordinator cannot follow that subprocess `exec`, so a coordinator-only profile misses the actual workflow process. For this test only, the template's launch command in the VM worktree was changed to `python -m memray run --follow-fork -o /profile/template-load.bin -m src.services.execution.template_process ...`. The VM source change was never committed or pushed. This produced 200 child captures. One representative [raw child capture](results/2026-09-25-template-child-memray.bin) is retained; a second child gave the same Memray statistics.

That child made 34,721 allocations totaling 11.528 MB, with a **2.406 MB traced peak after fork**. These are allocator measurements, not child RSS or container working set. Its largest allocation sources were `ssl.create_default_context` (2.592 MB and 31,923 allocations), Redis socket reads (1.840 MB), Python imports (1.741 MB), and bytecode compilation (1.263 MB). The peak stack ran through `_execute_sync` → the fixture workflow → HTTPX request handling. The fixture creates a fresh `httpx.AsyncClient` for every execution, so the SSL-context churn is attributable to this fixture's client lifecycle; it does not establish a platform-wide hot path or justify changing arbitrary user workflows.

A separate coordinator capture over 1,000 executions reported 3.42 million allocations, 36.075 GB cumulative allocation size, and 166.918 MB traced peak. About 29.25 GB of short-lived allocation size was attributed to `asyncio` socket receive buffers; the high-water mark was dominated by imports/startup. Cumulative allocated bytes are **not** retained memory, network bytes, or RSS. The profiled 1,000-execution run completed 1,000/1,000 at 13.25 executions/s, but profiling overhead and shared-host contention prevent a throughput comparison with an earlier unprofiled run.

This profile identifies per-execution HTTP client construction and coordinator socket-buffer churn as *measurement leads*. Neither is yet an evidence-selected Go subsystem. The next memory decision needs production role/process working-set telemetry and a representative workload corpus; then a Python baseline change can be compared with the same end-to-end fixture if one of these paths remains material.
