# Issue 890 runtime recommendation, 2026-09-25

**Keep the Python platform and optimize measured bottlenecks.** No Go or Rust extraction is justified by the current evidence. This is a decision for the observed workload and current B3 deployment, not a claim that Python can never constrain a future subsystem.

| Evidence | What it supports | Limit |
| --- | --- | --- |
| The clean four-core mocked outbound-HTTP lab plateaued around 17–19 correct executions/s, with high-concurrency delay mainly before the workflow entered its running phase. | Queue/admission/setup work deserves attribution before a language change. | This short synthetic workflow does not represent the production duration and integration mix. |
| The agent/tool-loop fixture exposed API database-pool timeouts at concurrency 16; releasing the read transaction before a blocking wait removed the failures (8/20 to 20/20). | A narrow Python-path fix already improved correctness under load. | The two fixture revisions also differed in setup, so the latency numbers are not an isolated speedup claim. |
| A one→two→one process API-read bracket delivered 259/475/261 correct requests/s at concurrency 16, with API CPU 1.00/1.89/1.00 cores and max memory 325/654/325 MiB. | Process topology can recover substantial throughput for a CPU-bound route without a Go port. | It is one small authenticated route, not useful workflow executions or a production cost result. |
| Four→eight→four worker slots gave a noisy 12–30% synthetic c64 throughput gain and 15–28 MiB more worker memory. | No production worker-slot change is supported. | Other test stacks were active; client and renderer memory were absent. |
| A low-rate all-thread Python sample did not identify a concentrated business-logic CPU hotspot. | No evidence-selected Go subsystem exists yet. | Sampling overhead and collection errors prevent a definitive negative CPU profile. |
| CodSpeed simulation and new serialization walltime/memory jobs passed on the branch. | The small helper and contract cases now have continuing regression coverage. | CI uses Python 3.12, so its absolute numbers do not measure the deployed Python 3.14 runtime or B3 capacity; runner variance has not been measured. |
| Production recorded 3,069 successful executions over about 24.11 hours, with substantial publish→claim and claim→start waits in a 30-attempt sample. | End-to-end waiting and production mix matter more than a microbenchmark win. | Historical B3 instance-hours were not verified; a later readback found two instances. Observed use is not capacity, and plan-wide CPU/memory cannot attribute runtime roles. |

The [initial measurements](2026-09-25-initial-measurements.md), [worker-density bracket](2026-09-25-worker-density.md), and [API process-topology bracket](2026-09-25-api-process-topology.md) retain the commands, source revisions, caveats, and raw results. The currently pinned production image source and lab use the same Python 3.14 base digest, so an interpreter-version upgrade is not an untested easy alternative in this comparison.

Before revisiting Go, use the [bounded passive production telemetry rollout](https://github.com/MTG-Thomas/bifrost-infra/issues/1614) to compare anonymous route/workflow shape, per-role CPU and memory, queue/setup/persistence time, DB wait, external wait, and event-loop lag against the lab. The current two-instance plan blocks the existing single-instance protected runtime deployer, so the telemetry rollout remains a draft until a safe deployment path is reviewed. Repeat the worker-density comparison on a quiet host with the full client/renderer budget. A Go spike becomes warranted only if those measurements isolate a mechanical Python-bound subsystem and a semantically equivalent implementation can plausibly change real end-to-end capacity, latency, or an actual compute tier. Prove parity for results, validation, errors, timeouts, retries, idempotency, persistence, and claim order before comparing performance with realistic I/O restored. Rust remains deferred under the issue's stated gate.
