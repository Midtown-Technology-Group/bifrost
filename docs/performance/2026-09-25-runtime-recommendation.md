# Issue 890 runtime recommendation, 2026-09-25

**Keep the Python platform and optimize measured bottlenecks.** No Go or Rust extraction is justified by the current evidence. This is a decision for the observed workload and current B3 deployment, not a claim that Python can never constrain a future subsystem.

| Evidence | What it supports | Limit |
| --- | --- | --- |
| The clean four-core mocked outbound-HTTP lab plateaued around 17–19 correct executions/s, with high-concurrency delay mainly before the workflow entered its running phase. | Queue/admission/setup work deserves attribution before a language change. | This short synthetic workflow does not represent the production duration and integration mix. |
| The agent/tool-loop fixture exposed API database-pool timeouts at concurrency 16; releasing the read transaction before a blocking wait removed the failures (8/20 to 20/20). | A narrow Python-path fix already improved correctness under load. | The two fixture revisions also differed in setup, so the latency numbers are not an isolated speedup claim. |
| A one→two→one process API-read bracket delivered 259/475/261 correct requests/s at concurrency 16, with API CPU 1.00/1.89/1.00 cores and max memory 325/654/325 MiB. | Process topology can recover substantial throughput for a CPU-bound route without a Go port. | It is one small authenticated route, not useful workflow executions or a production cost result. |
| Four→eight→four worker slots gave a noisy 12–30% synthetic c64 throughput gain and 15–28 MiB more worker memory. | No production worker-slot change is supported. | Other test stacks were active; client and renderer memory were absent. |
| A fresh-heartbeat 4→16→64→4 external-HTTP sweep completed 800/800 correctly. Publish-to-claim p95 rose from 0.057 to 3.449 seconds at c64, then returned to 0.045 seconds. At c64 the worker used about 1.73 cores, the API 0.33, and PostgreSQL 0.22. | Queue/admission delay appeared before CPU saturation and recovered without restart. | Shared-host samples and heartbeat lag do not isolate the first queue bottleneck or establish B3 capacity. |
| A follow-up [role-budget sweep](2026-09-25-role-budget.md) ran the same fixture with production-pinned client and renderer containers. At c64 the five application roles used at most 764.6 MiB simultaneously in sampled cgroup memory; the idle client and renderer accounted for 41.6 MiB. All 800 executions were correct and c64 queue p95 was 2.92 seconds. | The lab now includes the idle memory cost of all five production application roles. | Client and renderer did no representative work; host and dependencies still differ from B3, and the test-only API replica is excluded. |
| A [full 1→128 ramp](2026-09-25-full-ramp.md) completed 1,400/1,400 correctly. Throughput flattened near 16–17/s from c16 onward; publish-to-claim p95 rose to 7.13 seconds at c128 while running-to-terminal p95 stayed near 0.21 seconds. A final c4 step recovered to 16.69/s and 0.04-second queue p95 without restart. | The fixture's high-concurrency degradation is mainly before claim, with observed recovery and no demonstrated four-core CPU ceiling. | Other stacks were active; one-second worker samples do not isolate the first queue bottleneck, and this is not a B3 capacity figure. |
| A low-rate all-thread Python sample did not identify a concentrated business-logic CPU hotspot. | No evidence-selected Go subsystem exists yet. | Sampling overhead and collection errors prevent a definitive negative CPU profile. |
| CodSpeed simulation and serialization walltime/memory jobs passed. A docs-only PR nonetheless reported a 97.85% walltime improvement on one case. | The cases provide regression wiring, while the docs-only control exposes hosted-runner variance. | CI uses Python 3.12 and one noisy comparison cannot measure Python 3.14 B3 capacity or justify a Go port. |
| Production recorded 3,069 successes over at least 24.11 one-instance B3-hours, or at most about 127 observed successes/B3-hour; a 30-attempt sample had substantial publish→claim and claim→start waits. | Production mix and end-to-end waiting matter more than a microbenchmark win. | The query finish time was not recorded, observed use is not capacity, and aggregate CPU/memory cannot attribute runtime roles. Current plan capacity is two. |

The [initial measurements](2026-09-25-initial-measurements.md), [worker-density bracket](2026-09-25-worker-density.md), [API process-topology bracket](2026-09-25-api-process-topology.md), [admission sweep](2026-09-25-admission-observation.md), [role-budget sweep](2026-09-25-role-budget.md), [full 1→128 ramp](2026-09-25-full-ramp.md), and [production compute denominator](2026-09-25-production-compute-denominator.md) retain the commands, source revisions, caveats, and raw results. The currently pinned production image source and lab use the same Python 3.14 base digest, so an interpreter-version upgrade is not an untested easy alternative in this comparison.

Before revisiting Go, use the [bounded passive production telemetry rollout](https://github.com/MTG-Thomas/bifrost-infra/issues/1614) to compare anonymous route/workflow shape, per-role CPU and memory, queue/setup/persistence time, DB wait, external wait, and event-loop lag against the lab. The current two-instance plan blocks the existing single-instance protected runtime deployer, so the telemetry rollout remains a draft until a safe deployment path is reviewed. Repeat the worker-density comparison on a quiet host with the full client/renderer budget. A Go spike becomes warranted only if those measurements isolate a mechanical Python-bound subsystem and a semantically equivalent implementation can plausibly change real end-to-end capacity, latency, or an actual compute tier. Prove parity for results, validation, errors, timeouts, retries, idempotency, persistence, and claim order before comparing performance with realistic I/O restored. Rust remains deferred under the issue's stated gate.
