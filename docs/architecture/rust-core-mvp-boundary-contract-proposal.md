## Source constraints and compatibility

Actual `core-rs/crates/bifrost-contracts/src/runtime/control.rs` has only Hello/Start/Heartbeat/Cancel/Stopped; Start is `{prepare_message_id, committed_start_id, parent_duration_seconds: Positive}`. `session.rs::PreparedBinding` is parent-supplied assertion, not wire Prepare; `StartAuthorization` cannot verify a database commit. `ControlSession` accepts exactly `control_profile/v1`; sequence starts at one per direction and Start correlation equals prepare_message_id. Preserve these types, unknown-field rejection and all P0 vectors unchanged.

Main `contracts/runtime/v1/language-neutral/{artifact,workload,provision-binding}.schema.json` has independent document types and a common binding `{execution_kind,execution_id,attempt_id,attempt_number,session_id,caller_id,organization_id,solution_id,deployment_id,artifact_id}`. It lacks original-org provenance, accepted closure, supervisor and committed-Start facts. Do not pretend this binding is complete authority, or attach extras to its closed objects. Proposed expanded execution profile is a separately negotiated, closed schema alongside P0, with exact version/name to ratify in its schema packet. P0 alone cannot execute it. Timeout-zero requires an explicit expanded finite-or-unbounded duration type; do not encode zero into Positive, invent a deadline or silently reject existing no-timeout behavior.

## M1: common records and admission interface

Notation: UUID is canonical lowercase in the proposed private protocol; existing public parsing is unchanged; workflow attempt_number is 1..2147483647 (CRED-P1 bound). Timestamps use existing CRED UTC epoch-us conversion/private bounds. Every named nullable field is present with null; omitted source evidence keys remain omitted in the retained native evidence object, never normalized. All records reject unknown fields. Private claim tokens, JWTs/provider material stay out of public bindings, hashes exposed to children, logs and report data.

`ExecutionBinding` required fields: execution_kind=`workflow|agent_run`; logical_id; typed_attempt_kind=`workflow_execution_attempt|agent_execution_attempt`; attempt_id; attempt_number; owner=`rust`; owner_assignment_id; supervisor_incarnation_id; runtime_session_id; runtime_incarnation_id; trusted process_identity; workflow_id for workflow / agent_id for agent; caller_snapshot_digest; effective_organization_id; accepted_source_digest; runtime_artifact_digest; preparation_digest. Parent fills every identity; child can only echo. Agent attempt lease_token remains nullable and private; it is not a workflow claim token.

`CallerSnapshot` exactly uses CRED `AuthorizedCallerSnapshot`: caller_user_id, caller_organization_id, effective_organization_id, caller_email, caller_name, caller_admin, caller_provider, caller_external, roles (sorted unique bounded literal strings). Producer: trusted submit/admission authorization; verifier: Rust admission and accepting Python grant service. Missing original org is UNKNOWN, not known-null GLOBAL; such historical work remains on the Python route before admission. AUTH-P1 propagates provider privilege but does not repair original-org history.

`AcceptedSource` required: source_kind (first package only `solution-deployment`); source_id=accepted deployment UUID; solution_install_id; workflow_id; source_manifest_digest; source_resolution_digest; source_global_permission; native runtime_evidence object and runtime_evidence_hash; dependencies and resource/module closure entries from validated manifest/resolution; staged_closure_digest. Retain native manifest/hash algorithms and prefixed/bare values at their existing boundaries. Closure entries identify native logical/storage path, kind, namespace/package semantics, content digest and byte length; table and closure canonicalization require vectors against `deployment_manifest.py`, `deployment_runtime.py`, loader and resources. No current deployment pointer can rewrite accepted source_id. Workspace-release grant/source support is a later reviewed adapter, not this first package.

`AdmitWorkflow(request)` trusted request contains request_id, request_digest, workflow_id, exact parameters/input and native schema digests, original/effective CallerSnapshot, accepted source, source-observed Context projection, source limits including nullable/no-timeout values, existing dispatch/event/sync metadata, artifact selection, configured supported profile. Rust owns authorization refresh and source-accounting shared lock (`async_executor.py::_pin_execution_dispatch_evidence`, `workspace_release_projection.py::acquire_runtime_admission_lock`) before native row locks. Commit immutable owner, native execution/dispatch attempt, accepted evidence and source obligation together. `AdmissionReceipt` = request_id/request_digest, owner_assignment_id, logical_id, typed attempt identity, accepted_source_digest, caller_snapshot_digest, committed_at. Same identity+digest returns same receipt; conflict denies. Unsupported profile routes before this commit; accepted Rust work cannot redispatch to Python.

## M2: preparation, workload and hash interface

`Prepare` frame body = ExecutionBinding, prepare_message_id, workload_input (native input/schema digests/deadline_utc), exact source-observed context document+digest, limits document+digest, selected closed capabilities+digest, staged-source manifest+digest, selected runtime artifact document+digest, opaque provision_slot_id. No credential bytes. The private channel supplies session/process binding and per-direction sequence/correlation. Parent verifies staged bytes and authority before launch; Python only verifies bytes/metadata. Prepared body = prepare_message_id, preparation_digest, actual artifact observation (artifact_id, image_digest nullable, interpreter implementation/version, SDK distribution/version nullable, requirements_lock_sha256 nullable, runtime_protocol), actual closure observations+digest, runtime_incarnation_id. Parent rejects mismatches before Start. Prepare executes no tenant import, site/package/install hook, registration discovery or provider call.

Candidate receipt hash algorithm: SHA-256 of exact bounded validated UTF-8 document bytes, with message identity/type/session/start included in hashed envelope; persist bytes with receipt and return prefixed digest. Retransmission must use identical bytes; semantic equivalence with different bytes is a conflict. This avoids inventing cross-language float canonicalization. Native source hashes and CRED ordered digests stay unchanged. Schema vectors must freeze exact serialization and preserve native default=str/result byte accounting; this candidate algorithm is not already approved protocol.

Workload reports reuse separate language-neutral meanings: result success value or error `{code,message,details}`, log batches `{batch_sequence,entries[level,message]}`, usage measurements. Their current bounds (logs <=256, message <=16384 characters, usage <=64 integer measurements) are not a substitute for native result limits or provider decimal cost. Expanded profile must carry the full native result/status/error/null/omission/log metadata plus decimal cost and accounting evidence, without truncating whole result into model/step limits. Implement bounded chunking for an allowed native payload exceeding a frame, with total length/digest and complete reassembly before acceptance; frame/aggregate limits must be frozen against existing limits, not newly imposed on public results.

## M3: transition owners, Start and provision

| Transition/interface | Sole authority and required receipt |
|---|---|
| Admitted→claimed | Rust under immutable row owner; native workflow claim token/worker incarnation, policy/dispatch/runtime hashes. Claim receipt binds attempt/number/worker; delivery lease remains separate. |
| Claimed→session_open | Rust records one runtime_session_id, supervisor/runtime/process identity, preparation digest/slot and open timestamp; trusted pool adapter reports actual launch. Unique current session per attempt, no UUID-only live claim. |
| Session_open→prepared | Python byte/artifact observation; Rust durable PreparedReceipt binds session/prepare/preparation/artifact/closure hashes and accepted identities. |
| Prepared→Start committed | Rust refreshes owner, attempt, session, caller, accepted source and cancellation. Atomically records unique committed_start_id, exact prepare identity/digests, slot/capabilities, predeclared expiry/deadline, native started_at and running/phase=execution. StartReceipt includes that full binding plus committed_at and native fence. |
| Start committed→grant created | Python-owned trusted CRED service uses independent committed precheck and `_read_work` full locked refresh; no shared caller transaction. `CommittedWorkflowStart` fields remain exactly execution_id, workflow_attempt_id, attempt_number, private_claim_token, worker_incarnation_id, supervisor_incarnation_id, runtime_session_id, committed_started_at_us, timeout_seconds, predeclared_credential_deadline_us, predeclared_initial_access_expires_at_us. Source/caller/policy are the exact CRED private records. |
| Grant→provision admission/delivery | Rust owns live session/Start admission; Python signer/custodian owns signing and process-credential descriptor delivery. Durable ProvisionReceipt includes start/session/slot, grant_id/grant_digest, operations_digest, access expires_at, credential_deadline nullable, caller/source digests, admission_id/admitted_at; no token. Child ProvisionReady echoes this metadata and descriptor receipt, never proves database validity itself. |
| Execution permission | Python adapter requires accepted Prepared + owner-committed Start + same-binding actual provision before tenant module loading, hooks or effects. One Start only. Empty provision only for a genuinely grant-free profile, never fallback engine token. |

Session/provision records are new semantic requirements, not approved schema. Candidate transaction order: source-accounting shared fence first when admitting source; workflow attempt FOR UPDATE; native execution/deployment/install secondary SHARE NOWAIT as CRED does; owner/session/Start/grant/provision records in deterministic identity order, NOWAIT on contended secondary rows. Close/report/renew/adopt use the same attempt-first fence; no session-first close waiting on attempt. Contention aborts/rolls back complete transaction and is never workload retry authorization. Fresh locks revalidate every fact, never rely on earlier channel validation. Final schema package must prove order against incumbent execution-first writers and native event advisory lock; do not change CRED lock behavior silently.

`CloseSession(start/session, reason, expected fence)` is Rust authority. Commit persistent session-close tombstone (not deletion) and revoke existing grants atomically; closing before an absent grant prevents its later creation. Grant creation, issuance/provision admission, renew, report acceptance and tool adoption all refresh same tombstone/Start/owner/attempt facts. Signing/delivery after a previously winning admission can finish, but no new admission or usable future SDK operation may pass committed close. SDK request admission must check close fresh, not merely token signature. Already admitted vendor effects can finish; no locks across vendor calls and no claimed retroactive effect rollback.

Readmission: tombstoned session never reopens. Same-binding duplicate grant/receipt returns the existing durable result if identical; it does not renew authority. Any new session/attempt requires explicit native recovery eligibility with evidence no possible Start/effects, and a new preparation/start identity. After committed or uncertain Start, no replacement session, automatic replay or Python fallback is authorized. This requires new session-gate integration beyond current UUID snapshots.

## M4: result/projection receipts and mechanical mixed-writer exclusion

`AcceptReport` required: ExecutionBinding, message_id, message_type, committed_start_id, start_message_id, per-direction sequence, correlation_id where schema requires, validated payload bytes/length/digest, stream/batch identity and prior watermark where applicable. Rust checks trusted channel and fresh owner/attempt/Start/session/cancel frontier, inserts durable receipt unique(session_id,start_id,message_type,message_id), then native projection in the same transaction or guarded idempotent projection keyed to receipt. Exact duplicate returns prior ReportReceipt; digest conflict rejects. ReportReceipt includes receipt_id, binding_digest, payload_digest, acceptance disposition, accepted_at, projection watermark/native projection identity. Child result is observation: Rust selects native terminal state under existing status/race rules. No new public unknown status.

Mechanical exclusion candidate: immutable owner assignment bound to logical row and inherited by dependent attempts/logs/steps/usage/event projections; dedicated coordinator database principal distinct from incumbent Python and runtime principals; database-enforced checks on INSERT/UPDATE/DELETE by actual principal and row owner. Unforgeable caller identity must come from DB principal, never a session GUC the unrestricted Python role can set. Runtime receives no lifecycle SQL credentials. Incumbent consumer, cleanup, poison/recovery, HTTP/CLI completion and cancel paths cannot mutate Rust lifecycle rows even by direct DML. Request handlers invoke Rust owner operations instead. Rust cannot mutate Python-owned lifecycle rows. PgBouncer must retain verifiable distinct identities; shared superuser/table-owner bypass invalidates proof.

Field-specific summary/annotation/deletion permissions require separately named constrained operations; no whole-table summarizer exemption. Preserve existing summary status/delivery/asked/did/answered/confidence/metadata and usage. Rust owns durable event receipt/outbox and publication for Rust lifecycle; runtime reports observations only, no Redis publication/helper DML. Source drain remains open until trusted wait/reap of actual child/descendants and complete source-consumer closure, even after terminal/revoke. New roles/guard records/triggers/migrations and grants require concrete separate approval, not an implied extension of existing CRED migration.

## M5: cancellation, ACK-unknown and agent handoff

`RequestCancel` = request_id/digest, logical_id, owner_assignment_id, caller snapshot/current authorization, reason/source-native semantics. Rust commits cancel intent under same attempt/session/Start locks, returns CancelReceipt(cancel_id,fence,start_id nullable,committed_at,disposition), sends bound Cancel(reason,grace_ms), blocks new grants/renew/adoption as policy requires, revokes/closes and requires actual stop. Accepted result versus cancel is serialized under that fence; no unconditional success for a received result. Preserve native terminal mapping and race-surviving logs/usage. `Stopped` is protocol observation only; `StopReceipt` comes from trusted supervisor wait/reap and binds process/descendant evidence, session, reason, exit observation and source-consumer close.

Lost database commit ACK: reuse stable operation/request ID and query authoritative committed receipt through fresh session. Matching receipt establishes commit; unavailable readback remains unknown, denies effects/new admission. No Start or bearer material leaves custody until committed Start verified. A missing child ACK, lost provision, pipe loss or supervisor death after Start is possible execution; reconcile/revoke/stop the same binding, never resend workload or adopt a new Start. Lost terminal commit ACK reconciles same report receipt/projection; no second terminal/event/metering write. DB uncertainty does not prove cancellation or revocation and cannot manufacture worker_lost from child evidence.

Routing rollback closes new Rust admissions before queue change, retains immutable owners and in-flight source obligations, drains/reconciles existing work; no in-flight owner reassignment or started redispatch.

Agent next interface: ToolIntent(session/start,message_id,stable invocation_id,actual attached tool_id/schema_digest,arguments exact bytes/digest); Rust freshly authorizes attachment/original caller/effective scope and commits one intent receipt+child workflow admission atomically under source fence and same session gate. ToolOutcome binds intent receipt and actual child execution/terminal receipt, not a child-chosen execution ID. Python preserves actual tool formatting/model retry/fallback/budget behavior and reports real observation/next model request and ordered steps. Duplicate intent retains one child; conflict denies. Both unchanged tools/full schemas stay granted; first retained B invocation is capacity only. Agent closure includes native usage and separately owned summary delivery/metering. Agent provider/AI capabilities are not conferred by the two-operation CRED workflow grant.

## Independent review corrections and release gate

Independent source review holds the initial defaults as mechanically incomplete.
The workflow-first direction is accepted for further design; no schema or
execution owner is released. Required exact SQL/profile review must cover:

- Global admission request uniqueness before an owner exists; non-null owner
  keys for session-less receipts; composite session/owner and attempt/execution
  foreign keys. Independent foreign keys cannot establish the same binding.
- Native row, immutable owner, attempt, source obligation and admission receipt
  inserted atomically. Prepared/Start receipt references must match that same
  owner, session and message type. A closed session never permits another Start
  for an attempt with possible or committed execution.
- First accepted receipt and native result/log/usage/event projection committed
  together. An asynchronous projector would need its own reviewed durable
  pending/complete protocol and must not be described as already projected.
- Public deletion retains the minimum nonsecret owner/session-close/idempotency
  tombstones needed to fence late traffic and reconcile uncertain commits.
  Existing cascade rules must not silently erase authority evidence; any changed
  public deletion behavior requires its separate decision.
- Exact incumbent writer, reader, FK/cascade and lock catalog; actual distinct
  non-escalating PgBouncer backend identities. Missing entries block rollout.
  Custodian locked reads need only their narrow accepted operation, not blanket
  lifecycle write authority.
- Explicit coordinator read/ANY-table-lock disposition. Recommend retaining
  legitimate coordinator reads and native lock behavior with wrong-owner DML
  guards, subject to security approval and fail-closed outage/lock-delay tests.
  Runtime children still receive no SQL credentials. A broad stored-operation
  rewrite is conditional on rejecting that disposition, not an assumed task.

The PostgreSQL [LOCK privilege rules](https://www.postgresql.org/docs/16/sql-lock.html)
confirm that UPDATE/DELETE grants permit all table-lock modes. The
[trigger contract](https://www.postgresql.org/docs/16/sql-createtrigger.html)
provides no SELECT trigger, and
[constraint rules](https://www.postgresql.org/docs/16/ddl-constraints.html)
require special handling of null uniqueness and composite references. These are
source-level design constraints, not executed database evidence.

The next concrete deliverable is the bounded migration/role/profile diff and
its writer/reader/lock matrix for approval and supported characterization.
Do not request generic permission to continue, launch another exhausted
transport experiment, or start the workflow owner on incomplete defaults.
